## Хронология и что выяснено

### Этап 1. Первый запуск (24.10, утро)

Шлюз был в режиме `Modbus TCP to RTU`, TCP Server, порт 4196, 9600 8E1.
Контроллер читался: 15 из 15 регистров, уставка 5.0 °C.

**Найденные грабли:**
- Чётность должна быть **Even** — с `None` контроллер молчит полностью.
- Адресация Danfoss: **адрес регистра = PNU − 1**. Уставка `r00` = адрес **99**.
- Уставку ограничивает параметр **`r02`** (макс. ограничение, адрес 101).
  При `r02 = 3.4 °C` запись 5.0 отклоняется с `ILLEGAL DATA VALUE`.
  Решение: поднять `r02`, затем писать `r00`.

### Этап 2. Первый сборщик (24.10, день)

Написан `collector.py` — Python-скрипт без зависимостей:
опрашивает шлюз по Modbus TCP, собирает JSON, публикует в MQTT.
Проверен на 21 регистре, данные дошли до PostgreSQL.

**Что умеет:** ранний выход при отсутствии связи, переподключение к брокеру,
паспорт шлюза в каждом сообщении (MAC, прошивка, режим, серийные параметры),
пользовательские метаданные из `collector.json`.

### Этап 3. Попытка MQTT+JSON в шлюзе (24.10, вечер)

Три неудачные попытки, затем успех.

**Что пробовали и что не работало:**

| **Фиксированная строка, без RS485** | то же |
| Work Mode = TCP Server | MQTT-клиент **не запускается вообще** |

**Что сработало:**

### Этап 4. Два контроллера (24.10, вечер)

Значения разные (уставки 3.0 и 12.0) — значит оба контроллера реально опрашиваются.

## Технические открытия, которые важно не потерять

### 1. Transfer Protocol = None — обязательное условие

В режиме `Modbus TCP to RTU` шлюз работает **преобразователем**: принимает
Modbus TCP на 4196 и транслирует в RTU. Движок JSON в этом режиме не стартует.

**Симптом ошибки:** `akcc55-gateway` подключается к брокеру, PINGREQ идут,
`Received PUBLISH` — ноль. Порт 4196 при этом остаётся открытым — это подсказка.

### 2. Work Mode = TCP Client — обязательное условие

В режиме `TCP Server` MQTT-клиент не запускается. Проверено экспериментом:
смена режима дала подключение к брокеру мгновенно.

### 3. Конфигурация хранится в текстовых файлах

В папке дизайна Vircom:

| Файл | Содержимое |
|---|---|
| `mqtt.txt` | **открытым текстом**: `CLIENT_ID`, `PUBLISH_TOPIC`, `PUBLISH_QOS`, `KEEPALIVE` |
| `json` | бинарный дизайн; по строковым смещениям видно, какие ключи загружены (шаг записей 228 байт) |
| `httpd.txt` | настройки устройства, **зашифрованы**, не читаются |

`mqtt.txt` можно править файлом, не заходя в GUI.

### 4. Формат CSV для импорта дизайна

Заголовок — 23 колонки, строки — **24 поля** (особенность формата).

| Колонка | Значение |
|---|---|
| Data Source | `Modbus RTU`, **`Fixed String`** (с заглавной S), `Nested JSON`, `Device ID`, `Current time` |
| Data Format | `Signed int` |
| Modbus Slave Addr. | адрес контроллера |
| Modbus Function | `3` |
| Query Period | `100` |
| последнее поле | `255` |

**Грабли:** `Fixed string` со строчной буквой не распознаётся, импорт молча
пропускается. Точные строки надо брать из выпадающих списков Vircom.

### 5. Загрузка MQTT-конфигурации ломает веб-интерфейс

Это задумано Waveshare: MQTT-страницы заменяют страницы настройки.
Восстанавливается архивом `2043_waveshare_web_zx`.

### 6. Вирком перезаписывает файл при экспорте

Кнопка «导出配置» (Export) пишет поверх выбранного файла **без предупреждения**.
При пустой таблице файл обнуляется до одного заголовка. Экспортировать только
в отдельный файл.

## Ошибки и ложные выводы (для истории)

Не всё шло гладко. Эти ошибки стоили времени, и их стоит помнить:

1. **«Сгорел RS485-порт шлюза»** — ложный вывод. Причина была в том, что мой же
   перебор скоростей оставил шлюз на 115200 бод в прозрачном режиме, а команда
   возврата настроек выполнилась при уже неотвечающем веб-интерфейсе и молча
   провалилась. Правило: **после любых изменений настроек шлюза перечитывать
   конфигурацию** (`gateway_restore.py --verify-only`), а не верить ответу
   «Success! restart».

2. **Угадывание значений в CSV** (`Fixed string` вместо `Fixed String`) —
   импорт молча не срабатывал, а я строил на этом выводы.

3. **Лишние действия на объекте** — просил ставить перемычку A–B, менять провода,
   передёргивать питание, когда причина была в настройках.

4. **Неверная гипотеза о «ВМ остановлена»** — сервер был жив (контейнеры
   `Up 6 days`), недоступность была кратковременным сетевым сбоем.

1. Флаг ошибки датчика → связанные температуры становятся `null`
   (поэтому `evap_temp: null`, а не `-267.9`).
2. Значение вне −100…150 °C → `null`.
3. `main_switch: 1` → `true`.

### Известные ограничения

| Проблема | Суть |
|---|---|
| **Мультиконтроллерность** | `values` заполняется только для «чистых» ключей. Второй контроллер лежит в `raw.c2_*` и в `values` не попадает |

## Как вернуть систему в работу

### Если шлюз выключен
Подать питание, подождать минуту. Публикации пойдут автоматически,
база начнёт заполняться.

### Если нужно вернуться к схеме со сборщиком
```powershell
# 1. Прошить штатную прошивку через Vircom (Program File Download → 1.523(2007).BIN)
# 2. Загрузить веб-страницы (web directory download → 2043_waveshare_web_zx)
# 3. Настроить шлюз
python gateway_configure.py --set wkm=0 --set lcp=4196 --set ptc=1
python gateway_restore.py --file backup_collector_20261024\gateway_config.txt
# 4. Запустить сборщик
run_collector.cmd
```

### Проверка, что данные идут
```powershell
ssh yc-vm "docker exec it-kratos-db psql -U kratos -d telemetry -c 'select count(*) from telemetry'"
ssh yc-vm "docker exec it-mosquitto grep 'Received PUBLISH from akcc55-gateway' /mosquitto/log/mosquitto.log | tail -3"
```
